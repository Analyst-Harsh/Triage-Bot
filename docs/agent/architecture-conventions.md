# Architecture & module conventions — full detail

The detailed state-schema architecture and the module layout / testing / typing conventions that `AGENTS.md` points to. For the pipeline/vision level (why two entry points, the five-step pipeline, what makes it "production"), see `docs/summary.md` — this doc is one level more concrete: it's about how the code implementing that vision is organized.

## Architecture: state schema (`graph/state.py`, `graph/schemas/`)

The data contract every graph node reads and writes, and what the Postgres checkpointer persists between steps:

- Top-level `TriageState` is a `TypedDict` (LangGraph-native, checkpointer-friendly). Every nested slot (`IssuePayload`, `PlannerOutput`, `ResearchFindings`, `DraftOutput`, `RiskAssessment`, `EpisodicMemoryHit`, `RunMeta`) is a Pydantic `BaseModel` for real validation. Nodes construct/validate the Pydantic model, then write it into the TypedDict slot on their partial-update return.
- `TriageState` has **no top-level `messages` key**. Tool-calling nodes (the Researcher, and any future node built the same way, e.g. a Drafter code-fix loop) are `AgentSubgraph`s (`graph/nodes/agent_subgraph.py`), each with its own **private** `messages` channel on its own `AgentLoopState` — absent from `TriageState`, so it starts empty every run and never propagates to the parent. This superseded an earlier design (top-level `messages` shared across nodes for "free" tracing): once the Researcher became a genuine nested `StateGraph`, that subgraph's own checkpoint namespace and OTel/Langfuse traces already carry the full trajectory, so sharing a top-level channel only bought cross-node scoping ambiguity and an ever-growing log re-serialized into every later checkpoint, for no added observability. Nodes still hand off typed contracts only (`PlannerOutput` → `ResearchFindings`, never raw message history); `ResearchFindings.tool_calls: list[ToolCallRecord]` is the typed, programmatically-derived distillation of a trajectory that downstream nodes actually consume.
- Draft actions (`graph/schemas/actions.py`) are a Pydantic discriminated union on `action_type` (`CommentAction` / `LabelAction` / `CloseAction` / `CodeFixAction`) rather than one loosely-typed dict, so an incomplete or mismatched action fails validation instead of silently producing a half-filled action. This design also functions as a prompt-injection mitigation — see `docs/agent/security.md`.
- Guardrail counters (`iteration_count`, `tool_calls_made`, `estimated_cost_usd`, `max_iterations`, `max_cost_usd`) live in `RunMeta`, since LangGraph's built-in `recursion_limit` caps graph steps but not $ spend. These are actually enforced, not just tracked: `check_budget` (`graph/nodes/utils/budget_guard.py`) runs before every simple node's `execute()` (`TriageNode.__call__`) and before every Researcher/Drafter subgraph invocation (`AgentSubgraph.prepare_node`), and `BudgetGuardMiddleware` (`graph/nodes/utils/budget_guard_middleware.py`) re-checks before each in-loop model turn inside those two subgraphs, since a multi-call loop can blow through budget between the coarser per-node checks. A trip raises `BudgetExceededError` (`graph/errors.py`), which flows through the same `handle_node_error` path as any other node exception (`status=FAILED`, logged as a distinct `budget_exceeded` event) rather than a special propagation mechanism. `RunMeta` also tracks `cache_read_tokens`/`cache_creation_tokens` — the provider-reported OpenAI prompt-cache breakdown of every LLM call in the run, accumulated the same way as `estimated_cost_usd` via `with_usage()`. Both default to `0`, so a checkpoint written before these fields existed still deserializes cleanly. Observability only: the cache-read discount is already priced into `estimated_cost_usd` (see `llm/pricing.py::estimate_cost_usd`), never applied twice. `AgentSubgraph`'s private `AgentLoopState` (`graph/nodes/agent_subgraph.py`) carries the matching `summarize_cache_read_tokens`/`summarize_cache_creation_tokens` channels alongside `summarize_cost`, for the same reason.
- `episodic_context: list[EpisodicMemoryHit]` holds only the current run's retrieved matches. The persistent store itself (Postgres/pgvector) lives outside this schema, in `utils/episodic_memory_store.py` — see "Episodic memory" below.
- Both entry points (webhook and replay) construct state identically via `graph.state.create_initial_state()` — don't duplicate init logic between them.

## Structured-output validation: JSON Schema + Pydantic (`llm/structured.py`, `graph/schemas/base.py`)

Every LLM structured-output call goes through `call_structured()`, which forwards a `method` to LangChain's `with_structured_output()` — this controls what the *provider* enforces at generation time, separate from what Pydantic enforces on receipt:

- `method="function_calling"` (the default): the JSON Schema derived from the Pydantic model is a hint the provider biases sampling toward, not a guarantee. Required for `DraftProposal`/`ProposedAction` (the Drafter's main draft call) because their `action: DraftIntent` field is a discriminated union, which Pydantic compiles to `oneOf` + a `discriminator` keyword — OpenAI's strict Structured Outputs mode doesn't support `oneOf`, and (verified against the installed `langchain-core`) even `strict=True` on the `function_calling` path doesn't correctly harden every union branch, since `_recursive_set_additional_properties_false` doesn't recurse into `oneOf`. Pydantic's own validation (in particular `extra="forbid"`, see below) is the load-bearing enforcement for this schema, not defense-in-depth on top of a provider guarantee.
- `method="json_schema"`: OpenAI's strict Structured Outputs — a real constrained-decoding guarantee, including enforcing `Field(ge=..., le=...)`/`Field(min_length=...)` at generation time. Used at every call site whose schema has no discriminated union: `PlannerNode` (`PlannerClassification`), `RiskCheckNode` (`RiskJudgmentBatch`), `ResearcherSubgraph`'s `summarize_node` (`ResearchSummary`, via `summary_schema_method`), and the Drafter's independent grounding self-check (`GroundingCritique`). `DrafterSubgraph` keeps the `function_calling` default for its main `summarize_node` call (`DraftProposal`).
- Every schema under `graph/schemas/` inherits `StrictBaseModel` (`graph/schemas/base.py`), which sets `model_config = ConfigDict(extra="forbid")` — this is what actually rejects an unexpected field the provider-side schema conversion didn't catch (e.g. a model emitting a full `CodeFixAction`-shaped payload under a `code_fix`-tagged `CodeFixIntent`). Applied uniformly, not just to LLM-facing schemas, so no future schema can forget it; also matters for external boundary payloads (`IssuePayload`, `ApprovalDecision`) that were never LLM output to begin with.

## Approval queue: conditional routing + interrupt/resume

`AutoPostNode` posts every LOW-risk drafted action and leaves everything riskier as `PostOutcome.QUEUED`. `route_after_auto_post` (`graph/nodes/routing.py`, wired into the graph in `graph/builder.py`), a conditional edge out of `auto_post`, sends the run to `approval_queue` only when at least one action is `QUEUED`; an all-LOW-risk run ends right after `auto_post` (`status=AUTO_POSTED`) and `ApprovalQueueNode` never runs. This keeps `ApprovalQueueNode`'s own contract pure — *if it runs, it always interrupts* — instead of making the pause conditional inside the node body, and keeps a trace free of a no-op approval step when nothing needed one.

`ApprovalQueueNode` uses LangGraph's `interrupt()`: the payload is a typed `ApprovalRequest` (`graph/schemas/approval_request.py` — pure data model) built by `ApprovalRequestBuilder.build()` (`graph/nodes/utils/approval_request_builder.py` — construction logic, deliberately kept out of the schema file; see the Module layout convention below) — one `QueuedActionSummary` per queued action, with risk level/reasoning, sandbox outcome, and (for `code_fix`) a diff capped at `DIFF_PREVIEW_MAX_BYTES` (the full diff always stays in state; only the interrupt payload is capped, and the cap is constructor-configurable on `ApprovalRequestBuilder`). The first execution raises at `interrupt()`, checkpointing the run; resuming with `Command(resume=...)` re-executes the node **from the top**, and `interrupt()` returns the resume value instead of raising. Everything above the `interrupt()` call is therefore pure reads/validation — no GitHub call, no state mutation — so re-running it on resume is harmless.

**The resume value is untrusted input.** It's supplied by whatever external surface resumes the graph, not produced internally, so it's validated as a trust boundary: `ApprovalDecision`/`ActionDecision` (`graph/schemas/approval_decision.py`) both set `extra="forbid"`, and `ApprovalQueueNode` additionally checks that the resumed decision's index set exactly matches the queued index set (no missing, no extra, no duplicates). A mismatch raises `ValueError`, which the graph-wide error handler turns into `status=FAILED` — a deliberate tradeoff (fail the run rather than re-interrupt) until a real approval surface (API/CLI/dashboard) validates before ever resuming.

Approved actions post via the same `ActionExecutor` `AutoPostNode` uses; rejected ones become `ActionPostResult(outcome=REJECTED, detail=<reviewer note>)`. Final status is `APPROVED_AND_POSTED` if anything was approved (even if that post then failed — the status records the human decision, per-action results record the truth), else `REJECTED`.

**Known exposure (documented, not solved here):** at-least-once posting on a crash mid-resume. If the process dies after `ActionExecutor.execute()` posts but before the node's superstep commits, re-invocation re-runs the node and re-posts. A code fix's deterministic branch name (`triage-bot/issue-{n}-{run_id.hex[:8]}`) makes that path effectively idempotent (`create_git_ref` collides → `FAILED`, no duplicate PR); a comment could still be re-posted. `AutoPostNode` has the same pre-existing exposure — not new to this feature.

**`main.py` is the interim manual approval surface** — no dashboard/API exists yet (see `docs/summary.md`'s ops-dashboard vision item). It's resume-aware: before ever constructing a fresh `TriageState`, it calls `graph.aget_state(config)` and checks `snapshot.next == (NodeName.APPROVAL_QUEUE,)`. This check is load-bearing, not defensive boilerplate — `thread_id` is deterministic (`f"{repo}#{issue_number}"`, `graph/state.py`), so invoking with a brand-new initial state while a prior run on that same thread is still paused silently starts an *independent second run* on the same thread rather than resuming the first (verified empirically: distinct `run_id`, `auto_post` re-executes, re-posting every LOW-risk action). If the probe finds a pending interrupt, `main.py`'s `resume_paused_run()` parses `snapshot.interrupts[0].value` back into a typed `ApprovalRequest`, prompts interactively per queued action (`collect_approval_decisions()`/`prompt_decision_for_action()`), and resumes via `Command(resume=<ApprovalDecision as JSON>)`; the same helper handles a pause hit mid-invocation (`"__interrupt__" in result`) within a single `main()` call. `ApprovalDecision` is validated locally before sending even though `ApprovalQueueNode` revalidates it server-side — `main.py` is itself now a boundary constructing that payload, not just a passthrough.

## Episodic memory (`utils/episodic_memory_store.py`, `graph/schemas/episode.py`)

`BaseEpisodicMemoryStore` (real `EpisodicMemoryStore` vs. no-op `NullEpisodicMemoryStore` when `Settings.episodic_memory_database_url` is unset — same optional-feature shape as `docmind_mcp_command`) is injected into `PlannerNode`, `AutoPostNode`, and `ApprovalQueueNode` via constructor, not a `get_x_client()`-style `lru_cache` singleton: `main.py` opens the backing store once via the `episodic_memory_store()` async context manager (mirrors `sqlite_checkpointer()`/`sandbox_toolset()`) and threads it through `build_graph(memory_store=...)`. All three nodes wrap it in the same `graph/nodes/utils/episodic_memory_gateway.py`'s `EpisodicMemoryGateway` rather than calling the store directly — see below. `SpamCloseNode` takes no `memory_store`: it always routes to `ApprovalQueueNode` rather than terminating a run itself, so that node is always the one that writes the episode.

`Episode.post_results` is `PostResults | None` (default `None`) purely for backward compatibility — an episode written before this field existed must still deserialize (see `test_deserializes_without_post_results_for_backward_compatibility`, `tests/graph/schemas/test_episode.py`). No current code path writes a `None`-post_results episode: `RunStatus.REJECTED` now has exactly one source, `ApprovalQueueNode` (a human rejecting a queued action), always with full `post_results`/`risk_assessment` data — unlike the old `SpamRejectedNode`, which used to write `post_results=None` for a run that never reached drafting/risk-check/posting at all before it was replaced by `SpamCloseNode`.

`EpisodicMemoryStore` is a thin wrapper around LangGraph's own `langgraph.store.postgres.AsyncPostgresStore` — the framework's long-term/cross-thread memory primitive, the intended complement to the checkpointer (short-term/per-thread) — rather than a hand-rolled Postgres layer. `AsyncPostgresStore.from_conn_string()` is itself an async context manager (drops straight into `episodic_memory_store()`'s shape); `.setup()` runs its own versioned migrations (safe to call every process start); semantic search is configured once via `PostgresIndexConfig(dims=..., embed=<OpenAIEmbeddings instance>)` and then just used through `store.aput(namespace, key, value, index=["issue_text"])` / `store.asearch(namespace_prefix, query=...)` — the store embeds and runs the pgvector (HNSW, cosine) query internally; `EpisodicMemoryStore` never computes or handles a raw embedding vector itself. Driver stack is `psycopg`/`psycopg-pool` (v3), not `asyncpg` — a deliberate choice: `AsyncPostgresStore` is built on `psycopg`, and using the framework's own store means not maintaining a second driver stack alongside it. Episodes are namespaced `("episodes", repo_full_name)` with `key=str(run_id)`; retrieval searches the flat `("episodes",)` prefix so similar issues surface across repos, not just within one.

The `langgraph-checkpoint-postgres` package added for this also ships `langgraph.checkpoint.postgres.aio.AsyncPostgresSaver` — the production Postgres checkpointer `graph/checkpointer.py`'s `sqlite_checkpointer()` docstring already flags as pending "once `api/` lands." No new dependency will be needed for that; not wired up yet, since it's a separate scope decision from episodic memory.

No new graph nodes or edges: `PlannerNode` calls `EpisodicMemoryGateway.find_similar()` before its LLM call and folds up to `episodic_memory_top_k` hits into the prompt (`format_episodic_context_for_prompt`, `prompts/planner.py`) — `PlannerClassification`/`PlannerOutput` stay schema-unchanged, the signal only shows up through `classification_confidence`/`investigation_plan`/`reasoning`. Retrieval failures (`EpisodicMemoryUnavailableError`, wrapping `psycopg.Error`/`OSError`/the embedder's `OpenAIError`) are caught narrowly inside the gateway and degrade to an empty history rather than failing the run.

Write-back happens on exactly one of two mutually exclusive paths per run, both gated on `not run_meta.dry_run` (dry-run/replay-testing invocations must never pollute real memory): `AutoPostNode` writes only when `status == AUTO_POSTED` (nothing was left queued — the run is actually finished); `ApprovalQueueNode` always writes once it resolves, since reaching the end of that node means the run's outcome is final either way. `route_after_auto_post` already guarantees these two write attempts never both fire for the same run. `graph/nodes/utils/episodic_memory_gateway.py`'s `EpisodicMemoryGateway` centralizes both directions of this shared "call the store, catch `EpisodicMemoryUnavailableError` narrowly, log and move on" logic that all three nodes need — a store failure must never fail a classification outright, nor retroactively fail a run whose GitHub actions already resolved.

`Episode` (`graph/schemas/episode.py`) is the persisted record — reuses existing models directly (`DraftedAction`, `RiskLevel`, `PostResults`, `RunStatus`) rather than parallel ones, dumped via `model_dump(mode="json")` as `aput`'s JSON `value`. `run_id` doubles as the store's item key: `aput` with the same `(namespace, key)` upserts (the store's own `PRIMARY KEY (prefix, key)`), so a node re-executed under this codebase's existing at-least-once-on-crash exposure overwrites with identical content rather than writing a duplicate episode.

## Observability: Langfuse tracing (`observability/tracing.py`)

A single `langfuse.langchain.CallbackHandler`, passed into the top-level `graph.ainvoke()` call in `main.py`'s `RunnableConfig`, is what produces the entire nested span tree: LangGraph propagates that config's callbacks into every node, every nested subgraph (the Researcher's/Drafter's own compiled `StateGraph`s), and every LLM/tool call inside them, via LangChain's own contextvar-based config propagation — no per-node code is required for that structural nesting. Same optional-feature shape as episodic memory: `Settings.langfuse_public_key`/`langfuse_secret_key` unset means every function in `observability/tracing.py` degrades to a no-op (no client constructed, no spans emitted), not an error.

**`build_callback_handler(trace_id: str | None = None)` must not be given a `trace_id` while `root_span` is already open around the call** — `main.py`'s path, and the only one that exists today. This was a real bug during development, not a hypothetical: the `CallbackHandler`'s own `_take_root_trace_context` always honors an explicit `trace_context` set at construction over whatever's ambiently current in OTel context, so passing `trace_id` there while `root_span` was *also* bound to that same `trace_id` produced two independent root-level spans in the same trace (verified against the installed SDK) — `root_span`'s own span, and the handler's top-level chain span, neither referencing the other as parent, since the handler never consulted ambient context at all. With no `trace_context` (the default), the handler's root chain span falls through to normal ambient nesting instead, attaching under whichever span is already current — `root_span`'s, since it wraps every `graph.ainvoke()` call. The parameter stays available for a future caller with no ambient `root_span` to nest under (e.g. a FastAPI resume-only handler that recovers `trace_id` from a checkpointed `RunMeta` and fires a single `ainvoke(Command(resume=...))`), where explicit `trace_context` is the only way to keep it in the same trace — not exercised by any caller today.

On top of that automatic structure, `tracing.py` adds two things:

- `root_span`: wraps `main()`'s whole run (issue fetch, both `graph.ainvoke()` calls across the interrupt/resume boundary, and the result-file write) in one span, bound to a **deterministic trace ID** (`create_trace_id`, seeded from `thread_id` — `repo#issue_number`, already deterministic). This is what `RunMeta.trace_id` is for: it's always populated (even when Langfuse isn't configured — the seed hashing is free), ready for a future out-of-process resume (once a real webhook/API surface exists) to re-derive the identical trace ID and continue the same trace instead of starting a new one.
- `node_span`: creates its own span for one node's body (`TriageNode.__call__`, `AgentSubgraph.assemble_node`) and enriches it with this repo's own cost/token accounting, namespaced `authoritative_*` wherever it's attached.

  This creates a **second, nested span** alongside the `CallbackHandler`'s own auto-created one for the same node dispatch — which looks redundant, and was in fact rejected once as exactly that (a first cut used `Langfuse.update_current_span(metadata=...)`, an "ambient current span" lookup, to enrich the auto-created span directly instead of creating a new one). That first cut turned out to be actively broken, not just cosmetically imperfect, confirmed empirically (a real graph run against an in-memory OTel span exporter, no network): the metadata landed on `root_span`'s span every time, never on the node's own. The mechanism: LangChain's async callback dispatch (`langchain_core/callbacks/manager.py::ahandle_event`) fires each handler's `on_chain_start` via `asyncio.gather`, so the Langfuse handler's `context.attach()` — the call that makes its new span "current" — runs inside an isolated `asyncio.create_task`. Per Python's `contextvars` semantics, a mutation made inside a spawned task's context never propagates back to the caller once that task completes, so by the time `RunnableCallable.ainvoke()` (`langgraph/_internal/_runnable.py`) resumes and calls our node body, "current" still points at whatever was ambient *before* the callback dispatch ran — the parent span, not the just-created per-node one. Holding a span object directly, created and updated within our own single coroutine, sidesteps this entirely: nothing about it depends on inheriting context across that task boundary, so the extra nesting is the accepted cost of getting the metadata to land in the right place at all.

  This accounting is also kept deliberately distinct from Langfuse's own per-generation cost estimate: Langfuse prices a generation from its own maintained model-price table, keyed off a model name it extracts heuristically from the LangChain object — it has no visibility into Anthropic's prompt-cache discount tiers, which is exactly what `llm/pricing.py::estimate_cost_usd` (the number `RunMeta`'s `max_cost_usd` guardrail actually enforces against) gets right. The two are never reconciled into one number — that would require intercepting the CallbackHandler's own per-generation span before it closes, which happens entirely inside `.ainvoke()`, before `call_structured` regains control to compute cost. Not worth the fragility: the node-level span is the right altitude for the authoritative total anyway (it's what the guardrail actually accounts against), and it's clearly labeled so a human reading a trace doesn't confuse it with Langfuse's own estimate.

`root_span` is a plain wrapped function, not Langfuse's own `@observe()` decorator — `@observe`'s span name is fixed at decoration time, which doesn't fit a name computed at each call site the way `root_span(name="triage_run", ...)` needs.

## `utils/`: GitHub client + applying a drafter code-fix diff

Top-level `utils/` holds shared infrastructure classes that don't belong to a single graph node: `utils/github_client.py` (`GitHubClient`, the sole boundary through which the app reads/writes GitHub) and `utils/diff_applier.py` (`DiffApplier`, applying a drafter's code-fix diff). This is a different package from `graph/nodes/utils/` (node-internal helpers like `ActionExecutor`, scoped to the node layer) — same name, deliberately, since both hold "supporting code that isn't itself a node/schema," just at different layers; don't confuse the two when adding something new.

`DiffApplier.apply(diff, base_files)` applies a unified diff strictly against known base file contents using the real `git` binary in an ephemeral, isolated repo (own temp dir, own git identity, `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` pointed at `/dev/null` so ambient machine gitconfig — e.g. a global `core.hooksPath` or `commit.gpgsign` — can never affect it), returning the post-apply content of every file the diff touched (`None` for a deletion). No diff-parsing or hunk-application logic is written here — a battle-tested tool already does that correctly, and a hand-rolled string-based applier was a real alternative considered and rejected (no maintained, typed package exists for it either). A `DiffApplier` instance is stateless beyond an optional constructor-configurable `timeout_seconds`. `GitHubClient.create_pull_request_from_diff` is the only consumer: it constructs its own `DiffApplier` in `__init__`, fetches each target file at the drafter's pinned `base_commit_sha`, calls `self._diff_applier.apply(...)`, then builds the PR via PyGithub's Git Data API (blobs/tree/commit/ref, then `create_pull`) — `git` itself is a runtime dependency of this path, not just dev/CI tooling.

## Module layout convention

One Pydantic model (or tightly related pair, e.g. `RunError`/`RunMeta`, or a request/decision pair like `ApprovalRequest`+`QueuedActionSummary`) per file under `graph/schemas/`, all re-exported from `graph/schemas/__init__.py`, so call sites only ever import from the `graph.schemas` package, never a submodule directly. Follow this pattern for any new schema additions rather than growing an existing file or importing from the submodule directly.

**`graph/schemas/` holds data models only — no construction logic.** A schema file may define a plain constant that documents one of its own field's contract (e.g. `DIFF_PREVIEW_MAX_BYTES`, referenced from `QueuedActionSummary`'s field description), but assembling a model from multiple other models/business inputs is not a schema's job, even as a "small factory function." That logic belongs with its caller — see `ApprovalRequestBuilder` (`graph/nodes/utils/approval_request_builder.py`), which builds `ApprovalRequest` for `ApprovalQueueNode` and originally lived in the schema file itself before being moved out for exactly this reason.

## Testing convention

`tests/graph/` mirrors the `graph/` layout. Every schema has a construction test and a JSON round-trip test (`model_dump_json` → `model_validate_json`). The discriminated union additionally has dispatch and rejection tests. `tests/graph/test_state.py` round-trips full `TriageState` instances through LangGraph's own `langgraph.checkpoint.serde.jsonplus.JsonPlusSerializer` (`dumps_typed`/`loads_typed`) — this is the check that actually matters, since it proves state survives what the Postgres checkpointer will do to it in production, not just that individual models validate. Any new state field should get this same round-trip coverage, not just a unit test of the field in isolation.

## Typing convention

`pyright` runs in `strict` mode across the **whole project** (`include = ["."]`, not an allowlist of specific paths — new code under `api/`/`tools/` gets checked automatically without touching config) (Pydantic v2's native `dataclass_transform` support means no plugin is needed, unlike mypy). `reportMissingTypeStubs` is disabled in `[tool.pyright]` — that check is about third-party library stub completeness (e.g. `langgraph`'s submodules have inconsistent `py.typed` coverage), not our own code's type coverage, so it's not worth failing strict mode over. Every function needs a return type annotation (including `-> None` for tests), and helper functions that accept arbitrary override kwargs (the `make_*(**overrides: Any) -> Model` pattern used throughout `tests/graph/schemas/`) type them as `**overrides: Any` with an explicit `dict[str, Any]` for the defaults — don't leave `**kwargs` unannotated.

## Adding a new top-level source directory

If you start putting code in a currently-empty directory (`api/`, `tools/`), nothing needs to change in `[tool.pyright]` or `[tool.ruff]` — both already scan the whole project by default and only exclude `.venv`/`__pycache__`/dot-directories.
