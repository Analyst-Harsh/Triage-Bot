# Architecture & module conventions — full detail

The detailed state-schema architecture and the module layout / testing / typing conventions that `AGENTS.md` points to. For the pipeline/vision level (why two entry points, the five-step pipeline, what makes it "production"), see `docs/summary.md` — this doc is one level more concrete: it's about how the code implementing that vision is organized.

## Architecture: state schema (`graph/state.py`, `graph/schemas/`)

The data contract every graph node reads and writes, and what the Postgres checkpointer persists between steps:

- Top-level `TriageState` is a `TypedDict` (LangGraph-native, checkpointer-friendly). Every nested slot (`IssuePayload`, `PlannerOutput`, `ResearchFindings`, `DraftOutput`, `RiskAssessment`, `EpisodicMemoryHit`, `RunMeta`) is a Pydantic `BaseModel` for real validation. Nodes construct/validate the Pydantic model, then write it into the TypedDict slot on their partial-update return.
- `TriageState` has **no top-level `messages` key**. Tool-calling nodes (the Researcher, and any future node built the same way, e.g. a Drafter code-fix loop) are `AgentSubgraph`s (`graph/nodes/agent_subgraph.py`), each with its own **private** `messages` channel on its own `AgentLoopState` — absent from `TriageState`, so it starts empty every run and never propagates to the parent. This superseded an earlier design (top-level `messages` shared across nodes for "free" tracing): once the Researcher became a genuine nested `StateGraph`, that subgraph's own checkpoint namespace and OTel/Langfuse traces already carry the full trajectory, so sharing a top-level channel only bought cross-node scoping ambiguity and an ever-growing log re-serialized into every later checkpoint, for no added observability. Nodes still hand off typed contracts only (`PlannerOutput` → `ResearchFindings`, never raw message history); `ResearchFindings.tool_calls: list[ToolCallRecord]` is the typed, programmatically-derived distillation of a trajectory that downstream nodes actually consume.
- Draft actions (`graph/schemas/actions.py`) are a Pydantic discriminated union on `action_type` (`CommentAction` / `LabelAction` / `CloseAction` / `CodeFixAction`) rather than one loosely-typed dict, so an incomplete or mismatched action fails validation instead of silently producing a half-filled action. This design also functions as a prompt-injection mitigation — see `docs/agent/security.md`.
- Guardrail counters (`iteration_count`, `tool_calls_made`, `estimated_cost_usd`, `max_iterations`, `max_cost_usd`) live in `RunMeta`, since LangGraph's built-in `recursion_limit` caps graph steps but not $ spend.
- `episodic_context: list[EpisodicMemoryHit]` holds only the current run's retrieved matches — the actual episodic memory store (Postgres/pgvector) is future work, not part of this schema.
- Both entry points (webhook and replay) construct state identically via `graph.state.create_initial_state()` — don't duplicate init logic between them.

## Approval queue: conditional routing + interrupt/resume

`AutoPostNode` posts every LOW-risk drafted action and leaves everything riskier as `PostOutcome.QUEUED`. `route_after_auto_post` (`graph/nodes/routing.py`, wired into the graph in `graph/builder.py`), a conditional edge out of `auto_post`, sends the run to `approval_queue` only when at least one action is `QUEUED`; an all-LOW-risk run ends right after `auto_post` (`status=AUTO_POSTED`) and `ApprovalQueueNode` never runs. This keeps `ApprovalQueueNode`'s own contract pure — *if it runs, it always interrupts* — instead of making the pause conditional inside the node body, and keeps a trace free of a no-op approval step when nothing needed one.

`ApprovalQueueNode` uses LangGraph's `interrupt()`: the payload is a typed `ApprovalRequest` (`graph/schemas/approval_request.py` — pure data model) built by `ApprovalRequestBuilder.build()` (`graph/nodes/utils/approval_request_builder.py` — construction logic, deliberately kept out of the schema file; see the Module layout convention below) — one `QueuedActionSummary` per queued action, with risk level/reasoning, sandbox outcome, and (for `code_fix`) a diff capped at `DIFF_PREVIEW_MAX_BYTES` (the full diff always stays in state; only the interrupt payload is capped, and the cap is constructor-configurable on `ApprovalRequestBuilder`). The first execution raises at `interrupt()`, checkpointing the run; resuming with `Command(resume=...)` re-executes the node **from the top**, and `interrupt()` returns the resume value instead of raising. Everything above the `interrupt()` call is therefore pure reads/validation — no GitHub call, no state mutation — so re-running it on resume is harmless.

**The resume value is untrusted input.** It's supplied by whatever external surface resumes the graph, not produced internally, so it's validated as a trust boundary: `ApprovalDecision`/`ActionDecision` (`graph/schemas/approval_decision.py`) both set `extra="forbid"`, and `ApprovalQueueNode` additionally checks that the resumed decision's index set exactly matches the queued index set (no missing, no extra, no duplicates). A mismatch raises `ValueError`, which the graph-wide error handler turns into `status=FAILED` — a deliberate tradeoff (fail the run rather than re-interrupt) until a real approval surface (API/CLI/dashboard) validates before ever resuming.

Approved actions post via the same `ActionExecutor` `AutoPostNode` uses; rejected ones become `ActionPostResult(outcome=REJECTED, detail=<reviewer note>)`. Final status is `APPROVED_AND_POSTED` if anything was approved (even if that post then failed — the status records the human decision, per-action results record the truth), else `REJECTED`.

**Known exposure (documented, not solved here):** at-least-once posting on a crash mid-resume. If the process dies after `ActionExecutor.execute()` posts but before the node's superstep commits, re-invocation re-runs the node and re-posts. A code fix's deterministic branch name (`triage-bot/issue-{n}-{run_id.hex[:8]}`) makes that path effectively idempotent (`create_git_ref` collides → `FAILED`, no duplicate PR); a comment could still be re-posted. `AutoPostNode` has the same pre-existing exposure — not new to this feature.

**`main.py` is the interim manual approval surface** — no dashboard/API exists yet (see `docs/summary.md`'s ops-dashboard vision item). It's resume-aware: before ever constructing a fresh `TriageState`, it calls `graph.aget_state(config)` and checks `snapshot.next == (NodeName.APPROVAL_QUEUE,)`. This check is load-bearing, not defensive boilerplate — `thread_id` is deterministic (`f"{repo}#{issue_number}"`, `graph/state.py`), so invoking with a brand-new initial state while a prior run on that same thread is still paused silently starts an *independent second run* on the same thread rather than resuming the first (verified empirically: distinct `run_id`, `auto_post` re-executes, re-posting every LOW-risk action). If the probe finds a pending interrupt, `main.py`'s `resume_paused_run()` parses `snapshot.interrupts[0].value` back into a typed `ApprovalRequest`, prompts interactively per queued action (`collect_approval_decisions()`/`prompt_decision_for_action()`), and resumes via `Command(resume=<ApprovalDecision as JSON>)`; the same helper handles a pause hit mid-invocation (`"__interrupt__" in result`) within a single `main()` call. `ApprovalDecision` is validated locally before sending even though `ApprovalQueueNode` revalidates it server-side — `main.py` is itself now a boundary constructing that payload, not just a passthrough.

## `utils/`: GitHub client + applying a drafter code-fix diff

Top-level `utils/` holds shared infrastructure classes that don't belong to a single graph node: `utils/github_client.py` (`GitHubClient`, the sole boundary through which the app reads/writes GitHub) and `utils/diff_applier.py` (`DiffApplier`, applying a drafter's code-fix diff). This is a different package from `graph/nodes/utils/` (node-internal helpers like `ActionExecutor`, scoped to the node layer) — same name, deliberately, since both hold "supporting code that isn't itself a node/schema," just at different layers; don't confuse the two when adding something new.

`DiffApplier.apply(diff, base_files)` applies a unified diff strictly against known base file contents using the real `git` binary in an ephemeral, isolated repo (own temp dir, own git identity, `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` pointed at `/dev/null` so ambient machine gitconfig — e.g. a global `core.hooksPath` or `commit.gpgsign` — can never affect it), returning the post-apply content of every file the diff touched (`None` for a deletion). No diff-parsing or hunk-application logic is written here — a battle-tested tool already does that correctly, and a hand-rolled string-based applier was a real alternative considered and rejected (no maintained, typed package exists for it either). A `DiffApplier` instance is stateless beyond an optional constructor-configurable `timeout_seconds`. `GitHubClient.create_pull_request_from_diff` is the only consumer: it constructs its own `DiffApplier` in `__init__`, fetches each target file at the drafter's pinned `base_commit_sha`, calls `self._diff_applier.apply(...)`, then builds the PR via PyGithub's Git Data API (blobs/tree/commit/ref, then `create_pull`) — `git` itself is a runtime dependency of this path, not just dev/CI tooling.

## Module layout convention

One Pydantic model (or tightly related pair, e.g. `RunError`/`RunMeta`, or a request/decision pair like `ApprovalRequest`+`QueuedActionSummary`) per file under `graph/schemas/`, all re-exported from `graph/schemas/__init__.py`, so call sites only ever import from the `graph.schemas` package, never a submodule directly. Follow this pattern for any new schema additions rather than growing an existing file or importing from the submodule directly.

**`graph/schemas/` holds data models only — no construction logic.** A schema file may define a plain constant that documents one of its own field's contract (e.g. `DIFF_PREVIEW_MAX_BYTES`, referenced from `QueuedActionSummary`'s field description), but assembling a model from multiple other models/business inputs is not a schema's job, even as a "small factory function." That logic belongs with its caller — see `ApprovalRequestBuilder` (`graph/nodes/utils/approval_request_builder.py`), which builds `ApprovalRequest` for `ApprovalQueueNode` and originally lived in the schema file itself before being moved out for exactly this reason.

## Testing convention

`tests/graph/` mirrors the `graph/` layout. Every schema has a construction test and a JSON round-trip test (`model_dump_json` → `model_validate_json`). The discriminated union additionally has dispatch and rejection tests. `tests/graph/test_state.py` round-trips full `TriageState` instances through LangGraph's own `langgraph.checkpoint.serde.jsonplus.JsonPlusSerializer` (`dumps_typed`/`loads_typed`) — this is the check that actually matters, since it proves state survives what the Postgres checkpointer will do to it in production, not just that individual models validate. Any new state field should get this same round-trip coverage, not just a unit test of the field in isolation.

## Typing convention

`pyright` runs in `strict` mode across the **whole project** (`include = ["."]`, not an allowlist of specific paths — new code under `api/`/`tools/` gets checked automatically without touching config) (Pydantic v2's native `dataclass_transform` support means no plugin is needed, unlike mypy). `reportMissingTypeStubs` is disabled in `[tool.pyright]` — that check is about third-party library stub completeness (e.g. `langgraph`'s submodules have inconsistent `py.typed` coverage), not our own code's type coverage, so it's not worth failing strict mode over. Every function needs a return type annotation (including `-> None` for tests), and helper functions that accept arbitrary override kwargs (the `make_*(**overrides: Any) -> Model` pattern used throughout `tests/graph/schemas/`) type them as `**overrides: Any` with an explicit `dict[str, Any]` for the defaults — don't leave `**kwargs` unannotated.

## Adding a new top-level source directory

If you start putting code in a currently-empty directory (`api/`, `tools/`), nothing needs to change in `[tool.pyright]` or `[tool.ruff]` — both already scan the whole project by default and only exclude `.venv`/`__pycache__`/dot-directories.
